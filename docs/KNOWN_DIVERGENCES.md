# Known divergences from the retail game

This list records behavior that is incomplete or has not yet been shown to
match the locally supported XANBUD release. The port must not be described as
1:1 while any item remains open. “Unverified” means there is no controlled
comparison with the retail executable in DOSBox (or equivalent captured
reference) for the behavior in question.

## Runtime and coverage

| Area | Current state | Evidence / reason | Closure evidence |
|---|---|---|---|
| Game logic execution | The current port executes the supplied retail `XANTH.EXE` and its overlay under a custom 8086/DOS VM. It does not yet dispatch into the decompiled C/assembly units: **0/2,844 indexed source units (0%) run as native game code**. | `port/src/emu/main_vm.c`, `port/src/emu/vm.c`; `port/CMakeLists.txt` does not link root `src/` decomp units into `xanth_port`. | Route game execution through recovered units, or document and verify the interpreter as the chosen preservation implementation. |
| Decompilation completeness | The 2,844-unit listing-splice rebuild has zero `_emit` byte-dump units and the project records `BINARY-MATCH` for both images. This is image reconstruction evidence, not proof that every function has semantic source or that the native port runs that source. A reliable total-function denominator is not currently recorded. | `python3 tools/coverage.py` reports 442 unaided-C, 959 mnemonic-assembly, 528 Watcom-assembly, 915 transcribed-data units, and 0 emit-dump units. The latest documented `BINARY-MATCH` is dated 2026-09-19. A fresh 2026-09-29 `tools/verify.py` run reached the splice stage but stopped because the historical MSVC 8.00c compiler is absent; `tools/coverage.py --compile` reports the same missing MSVC/Wine toolchain. | Restore the historical compiler for verification, rerun both gates, and publish a function inventory with a defined denominator and per-function source/match status; verify native execution on each claimed route. |
| Walkthrough | The documented, gated route ends at Fairy Nuff's booth with 122/1000 points. Later traces exist, but are not represented by an equivalent committed golden walkthrough gate. The full game and ending are not verified. | `README.md`, `docs/PORT.md`, `tests/test_walkthrough.py`, `tests/test_walkthrough_pail.py`. | Add deterministic checkpoints through all scenes and verify the 1,000-point ending against the retail route. |
| DOS compatibility | The VM implements the DOS, BIOS, mouse, VGA, PIT and audio services observed on current routes. Unused services and unvisited paths may differ or trap. | VM dispatch and conformance tests cover observed behavior; there is no whole-game DOSBox differential run. | Compare service traces, machine state and visible output over the complete route; record and close every mismatch. |

## Presentation and timing

| Area | Current state | Evidence / reason | Closure evidence |
|---|---|---|---|
| Graphics and text | Current frames are generated by retail guest code and local retail assets. Pixel-perfect parity against DOSBox has not been demonstrated across the complete game. | Deterministic VM frame hashes prove repeatability within this port only. | Side-by-side captures from the same release, route, input and frame/tick points. |
| Audio | OPL music and digitized paths are implemented in the HAL, but concurrent playback, timing, and sample-for-sample parity with the retail driver are not established. `adlib` is the configuration used for documented golden frames and does not play digitized audio. | `docs/PORT.md` audio section and `port/src/hal_audio.c`; no DOSBox audio capture comparison. | Compare decoded playback, timing and mixing with DOSBox for representative VOC, RealSound and music events. |
| Timing | Guest time is modeled from virtual cycles and host presentation targets 70 fps. This has not been compared numerically with the retail game under DOSBox. | `port/src/emu/main_vm.c`; `docs/PORT.md`. | Pin timing measurements for boot, animation, input response and audio against the retail reference. |

## Distribution and platforms

| Area | Current state | Evidence / reason | Closure evidence |
|---|---|---|---|
| Runtime asset validation | A first-run preflight checks the EXE and a hash manifest of 90 runtime assets before opening SDL. The manifest is pinned to the local XANBUD set; other releases are rejected. | `port/src/asset_check.c`, `port/include/retail_asset_manifest.h`; Linux Release build and one-frame boot succeeded with the supplied matching files. Missing and modified assets both failed before SDL with a filename and setup guidance. | Repeat startup validation on a Windows runner. |
| Platforms | Linux is the active development target. Windows build support is present in configuration/CI but has not been verified on a real Windows runner. Handheld targets are not implemented or validated. | `README.md`, `.github/workflows/port.yml`. | Record real-runner results per platform; make no handheld claim until tested. |
| Mods and optional configuration | Hash-keyed asset replacements are now opt-in through `--mods <dir>` and use files named for the original asset SHA-256. There is no mod manifest/load order, event-hook ABI, cheat implementation, or persistent user configuration yet. | `port/src/emu/main_vm.c`, `port/src/emu/vm.c`; a trace confirmed an opened asset resolves to the hash-named replacement path. A 200-frame BMP hash was identical with no mods and an empty mod directory (`f92193b1c9673df2e6e812e00cff51caf703afbfd81eef6d0921b7b936920df3`). | Demonstrate a visible valid asset change, repeat default parity through a gameplay checkpoint, add hook/mod metadata and cheats only behind opt-in settings. |
